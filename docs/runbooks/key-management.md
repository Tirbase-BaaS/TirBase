# Key Management Runbook — Domains, Rotation, Revocation, Recovery

> **Status:** Implemented. F-05. This runbook covers operational key
> management for the six key domains. Root CA generation, trust-root signing,
> and installation remain governed by [`docs/root-ceremony.md`](../root-ceremony.md);
> nothing here replaces or loosens that ceremony.

---

## 1. Key domains and custody

| Domain | Purpose | Custody | Export |
|---|---|---|---|
| `root-ca` | Trust anchor; authorises root rotation | Offline HSM / air-gapped media | Prohibited |
| `policy-authority` | Policy manifests, capability grants | Offline HSM | Prohibited |
| `update-signer` | Release and OTA artefacts | HSM (may be online) | Prohibited |
| `export-signer` | Export receipts and attestations | HSM | Prohibited |
| `device-identity` | Per-device credential | Device secure element / TPM | Prohibited |
| `tenant-wrapping` | Per-tenant envelope KEKs | KMS/HSM, versioned per tenant | Prohibited |

Every key is generated inside its custodian. `tirbase_core::keys::KeyCustodian`
exposes generate / sign / public-key / revoke / zeroize only; there is no
private-key export call. A deployment that requires key backup uses the
quorum-gated wrapped-export ceremony, never a runtime API.

Each domain is independent: records, validity windows, and revocations are
per-domain, and signatures are domain-separated
(`TirBase/v1/KeyDomain/<domain>\0<artefact>`), so an artefact signed for one
domain cannot be replayed in another.

---

## 2. Rotation

`KeyRegistry::rotate` performs the whole transition:

1. The new key is generated by the custodian and becomes `Active` at `now`.
2. Every previously `Active` key in that domain becomes `Retiring`, and its
   `not_after` is clamped to `min(existing not_after, now + overlap)`.
3. Old artefacts continue to verify until the overlap closes.
4. A `Retiring` key can never sign a new artefact (`KeyError::NotActive`), and
   after the window closes it verifies nothing (`KeyError::Expired`).

Recommended overlap: at least the maximum artefact TTL plus one distribution
interval (default 7 days for release artefacts, 1 hour for policy bundles).

Checklist:

- [ ] Overlap chosen from the artefact lifetime, not from convenience.
- [ ] New key custodied before rotation; public record registered.
- [ ] Rotation receipt archived (`previous_key_id`, `new_key_id`,
      `overlap_ends_at`).
- [ ] Old key material destroyed after the overlap, under audit hold or
      decommission receipt.

---

## 3. Revocation

Revocation is per key, not per trust root:

1. `KeyRegistry::revoke(domain, key_id, reason, now)` records the revocation
   and marks the record `Revoked`; no replacement key is minted.
2. `KeyRegistry::revocation_list()` produces the distributable
   `RevocationList`.
3. Each node calls `RevocationList::apply_to(&mut registry)`. Only the listed
   key ids are rejected; device identity and tenant wrapping keys are untouched.

Use `RevocationReason::KeyCompromise` for a suspected compromise, and rotate the
domain separately once a replacement is custodied. A compromised key must be
revoked **before** the replacement is announced, so there is no window in which
the attacker's key is the only active key.

Fleet impact: none. No device re-enrolment and no tenant re-wrap is required,
because the trust anchor and device credentials are unchanged.

If root keys or role keys beyond one domain are affected, escalate to
[`key-compromise.md`](key-compromise.md) and the root ceremony.

## 4. Recovery and disaster re-key

Both procedures require a `QuorumApproval`: `RecoveryOperation`, target domain,
distinct custodian approvals meeting the threshold, and an expiry. Minimum
production quorum is 2-of-3; no single custodian can start either procedure.

### 4.1 Recovery (trust anchor intact)

Use when a custodian share, HSM, or ceremony medium is lost.

1. Open the approval with `RecoveryOperation::Recover` and the affected domain.
2. Collect `threshold` distinct `CustodianApproval`s, each with a share
   commitment (never the share itself).
3. Call `KeyRegistry::recover` before the approval expires.
4. Verify the new key signs and the old artefacts still verify.

### 4.2 Disaster re-key (root compromised or destroyed)

1. Open the approval with `RecoveryOperation::DisasterRekey`, domain `root-ca`.
2. Collect the quorum and call `KeyRegistry::disaster_rekey_root`.
3. The call returns a `BridgeWindow`: the old root keeps verifying only until
   `not_after`, giving the fleet a bounded transition window.
4. Publish the new trust root per [`docs/root-ceremony.md`](../root-ceremony.md)
   §8, with a strictly greater version.
5. After the bridge closes, the old root verifies nothing. Destroy it per §6.

Never extend the bridge by editing the window: repeat the ceremony instead.

## 5. Zeroization

Two paths, both driven through the custodian:

| Path | Call | Result |
|---|---|---|
| Decommission | `KeyRegistry::decommission` | key destroyed, record `Destroyed`, `ZeroizeReceipt` |
| Compromised device | `KeyRegistry::compromised_device` | revoke (`KeyCompromise`) + destroy, `CompromiseRecord` |

Rules:

- Zeroization is idempotent; a replay returns `already_destroyed: true`.
- The public record and revocation history are retained so old artefacts fail
  closed and remain auditable.
- Never delete the record to "clean up": a missing record cannot be
  distinguished from a forged one.
- Record the receipt in the incident or decommission ticket.

## 6. Ceremony alignment

Root key generation, k-of-n signing, version rollback protection, and
installation are documented in [`docs/root-ceremony.md`](../root-ceremony.md)
and are authoritative for the `root-ca` domain:

| Root ceremony step | This runbook |
|---|---|
| §3 prerequisites / quorum `k`/`n` | §1 custody, §4 quorum policy |
| §4 generate root keys | §1 domains; `SoftwareCustodian::from_seed` only for dev |
| §5–6 build and sign the trust-root body | unchanged |
| §7 install with rollback protection | unchanged |
| §8 rotate root keys | §2 overlap rules; `rotate` |
| §9 revoke a root key | §3; `revoke` + new `TrustRootRecord` |
| §10 checklist | §2–§5 checklists |

The root domain uses the same rotation/revocation/zeroization machinery as the
other five domains, but the **artefact** it authorises is still the signed
`TrustRootRecord` installed by the gateway. A root rotation is not complete
until the new record is installed and the committed `trust_root_version`
advances.

---

## 7. Evidence to retain

- Rotation receipts for every domain, with overlap windows.
- Revocation list checksums and the time each node applied them.
- Quorum approvals, including custodian ids and share commitments (never
  shares or seeds).
- Zeroization receipts and compromise evidence references.
- Ceremony transcript per `docs/root-ceremony.md` §10.
