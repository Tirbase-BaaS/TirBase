# TirBase v0.1.0 — evidence and release gates

**Release date:** 2026-11-13
**Claims registry:** `CLAIMS.md` (411 rows: 403 Proven, 3 implemented and wired but unproven,
0 implemented but not wired, 5 Planned)
**Scope of this note:** what the claims in this release mean, which gates enforce them, and what
this release explicitly does **not** claim.

## What ships

- The Rust workspace (`tirbase-types`, `tirbase-core`, `tirbase-guard`, `tirbase-drivers`,
  `tirbase-gateway`, `tirbase-admin`, `tirbase-sim`, `tirbase-demo`) with the reference vertical
  demo packs.
- The generated gateway-admin TypeScript SDK and the `@tirbase/core-wasm` package sources.
- The claim registry, threat model, traceability matrix, adversary-scenario catalogue, and the
  operator/compliance documentation referenced from `CLAIMS.md`.

No binary, container image, or `.deb` is attached to this source release; the packaging claims
(`CLAIM-37.2`, `CLAIM-37.3`) are evidenced by their CI jobs, not by a published artifact.

## How the claims are enforced

| Gate | What it proves | Where |
|---|---|---|
| Claim registry schema | five columns, closed status vocabulary, every production-caller path reachable from a crate root | `scripts/check-claims.sh`, `scripts/check-claims-schema.py`, CI job `claims-check` |
| Cited evidence | every test identifier cited by a gated row resolves to a `fn`, `mod`, or `.rs` file; a `Proven` row may not cite an `#[ignore]`d test | `scripts/check-claims.sh`, CI job `claims-check` |
| Documentation claims | threat model, invariant catalogue, security-event catalogue, unit registry, and freshness policy still contain their promised sections/entries | `scripts/check-docs-claims.sh`, CI job `claims-check` |
| README agreement | the README status section is regenerated from `CLAIMS.md` and CI fails on drift | `scripts/generate-readme-status.py`, CI job `readme-status` |
| Remove-the-caller proofs | a security-critical test must fail when the production caller is removed, and pass again after restore | `docs/security-critical-callers.toml`, `scripts/reverse-proof.py`, nightly workflow `reverse-proof` |
| Traceability | every path named in the traceability matrix exists | `scripts/check-traceability-matrix.sh`, workflow `traceability` |

## Command ingress

All three ingress paths now have production receivers in `tirbase-gateway`:

- **Local admin** — `local_admin_command_addr` starts the loopback TCP JSON-lines receiver.
- **Cloud API** — the outbound-initiated channel (`cloud.rs`) receives `command` frames and admits
  them with `IngressSource::CloudApi`; there is still no inbound cloud listener.
- **Mesh** — signed commands travel as `GossipMessage::InboundCommand`
  (`CoreHandle::publish_mesh_command` / `subscribe_mesh_commands`). With
  `mesh_command_ingress = true` and a signed EnvelopeProfile installed, `main.rs` starts
  `command_ingress/mesh.rs::run_mesh_command_receiver`, which admits each command with
  `IngressSource::Mesh`. Delivery is not admission: signature, role, token, envelope,
  anti-replay and quorum are verified locally, and a gateway without a profile never starts the
  receiver. Proven by `inbound_mesh_command_is_delivered_to_subscriber` and
  `mesh_command_receiver_runs_every_command_through_admission` (CLAIM-35.7).

## Not done / not wired

- **`CLAIM-6.7b`, `CLAIM-52.2`, `CLAIM-52.3` — hardware-gated evidence.** TPM2/swtpm and HIL
  power-cut/Modbus tests are written but not executed in CI (RD-7 hardware, TPM2 host tooling).
  They are recorded as *implemented and wired (unproven)*, never Proven.
- **Planned items.** TUF adoption (`CLAIM-30.7`, `CLAIM-30.10`), lab hardware provisioning
  (`CLAIM-52.1`), fixed-point canonical-exponent enforcement coverage (`CLAIM-4.2`), and WAL
  checkpoint hardening (`CLAIM-32.4`) are Planned with an explicit blocker.
- **Independent review.** The crypto review and penetration test are scoped, not completed
  (`docs/crypto-review-scope.md`, `docs/pentest-scope.md`, `docs/security-findings.md`). No claim
  in this release rests on a completed external review.
- **SIL, CRA, IEC 62443.** No safety-integrity claim and no certification claim is made. The
  compliance documents are evidence for an operator's own assessment only.

## Known limitations of the evidence itself

- The production-caller column proves reachability (the module is compiled into a crate root),
  not that a specific runtime branch is exercised in every deployment configuration. The
  remove-the-caller proofs cover the four security-critical claims listed in
  `docs/security-critical-callers.toml`; the remaining Proven claims rest on their cited tests.
- Where a claim is backed only by a document, the evidence is the document plus the section check
  in `scripts/check-docs-claims.sh`.
- The phase audits under `docs/audits/` are dated records. A few rows written before the
  relevant tests landed still classify their task as `NOT IMPLEMENTED` or `BLOCKED`
  (`CLAIM-9.6`, `CLAIM-29.3`, `CLAIM-29.5`, `CLAIM-29.6`). Their current evidence is the test
  cited in `CLAIMS.md`; the audit rows have not been rewritten, so treat the registry as current
  and the audit text as historical.
- The `CLAIM-G1.9` reverse proof targets the revocation-application caller
  (`receive_revocation_delta` → `apply_revocation`). Under the current epoch-interrupt behaviour,
  removing the `finish_migration` re-check alone does not fail the integration test, so the claim
  text records that check as defence in depth rather than as the load-bearing caller.

## Upgrade notes

- `CLAIMS.md` now has a `Production Caller` column. Tooling that parsed the old four-column table
  must read the fifth column (`scripts/generate-readme-status.py` and
  `scripts/check-claims-schema.py` are the reference parsers).
- Status values are a closed vocabulary: `Proven`, `Implemented and wired (unproven)`,
  `Implemented but not wired`, `Planned`. `Implemented` and `Wired` are no longer valid.
