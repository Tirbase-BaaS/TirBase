# TirBase Verification Claims

This file is a **machine-readable registry** of every security and correctness claim in the TirBase
codebase.  Each row maps a `CLAIM-*` identifier (referenced from source code, tests, and CI steps)
to the claim text, its current status, and the integration test or CI gate that proves it.

**Status values:**
- `Proven` — the claim is backed by a passing integration test or CI gate; the test identifier is
  mandatory.
- `Planned` — the claim is committed to but the backing test has not yet been written; test
  identifier must be empty.

> **CI gate (CLAIM-3.1):** `scripts/check-claims.sh` runs on every push/PR and fails the build if
> any `Proven` row has an empty test identifier, or if a row cites a test identifier that does not
> resolve to a real `fn <name>`, `mod <name>` or `<name>.rs` in this repository.  A claim may only
> be `Proven` when the cited test exists; rename a test and you must update its citation here.
> Update this file whenever a test is added or a status changes.

## Task 35 Blocker Note

Task 35 requires three command ingress paths (local admin, mesh, cloud API). Only the
local-admin path exists as a transport in this repository, and it is now implemented
end-to-end in the real `tirbase-gateway` binary: `GatewayConfig.local_admin_command_addr`
starts a loopback TCP JSON-lines receiver (`command_ingress/local_admin.rs`) that calls
`admit_and_dispatch_blocking` (Stages 0–19) on the same `CommandGuard` instance the admin
API uses. `tirbase-gateway/tests/task35_binary.rs::claim_35_4_local_admin_signed_command_reaches_guard_and_moves_metrics`
proves a signed command receives a real guard decision and moves the Prometheus counters.

The mesh and cloud API command receivers are **not implemented**, because no such
transport exists anywhere in `tirbase-gateway` (there is no receiver loop, no command
message queue, and no cloud API server): `CoreHandle` is installed for the CRDT/transport
runtime, but it does not expose a gateway command ingress. They are not stubbed or faked
here. Implementing them requires a concrete transport crate/API that the codebase does
not currently contain, so the task 35 ingress checkboxes for mesh and cloud remain
unchecked until that transport exists.
