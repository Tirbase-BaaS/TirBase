# TriBase Verification Claims

This file records formally-verified or test-proven security and correctness claims.

| Claim ID   | Claim                                                                                                                                                                | Status | Test |
|------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------|------|
| CLAIM-1.3  | CI blocking steps enforce that `tirbase-core/Cargo.toml` does not declare `tirbase-guard` or `tirbase-drivers` as dependencies, and that `tirbase-drivers/Cargo.toml` does not declare `tirbase-guard` or `tirbase-core` as dependencies; each step greps the manifest and fails with a named violation message, then runs `cargo check -p <crate>` to compile-verify layer isolation; both the `check` and `test` CI jobs are gated on these steps via `needs: layer-isolation` | Proven | `layer-isolation` (`.github/workflows/ci.yml`) |
| CLAIM-2.2  | `deny.toml` at workspace root enforces: (1) all licenses are denied unless in the allow-list (MIT, Apache-2.0, Apache-2.0 WITH LLVM-exception, BSD-2/3-Clause, ISC, OpenSSL, Zlib, CC0-1.0, Unicode-3.0, Unicode-DFS-2016, MPL-2.0); (2) `openssl`, `openssl-sys`, and `native-tls` are banned; (3) all vulnerability advisories are errors (v2 mode); (4) only crates.io is an allowed source. The `cargo-deny` CI job runs `EmbarkStudios/cargo-deny-action@v2` as a blocking gate before `check` and `test` jobs (`needs: [cargo-deny, layer-isolation]`). Pre-existing advisories in the tree at gate-wiring time are individually documented in `deny.toml`'s `ignore` list with upgrade-tracking reasons. | Proven | `cargo-deny` job (`.github/workflows/ci.yml`), `deny.toml` |
| CLAIM-2.3  | `audit.toml` at workspace root lists all pre-existing advisories acknowledged at gate-wiring time. The `cargo-audit` CI job runs `rustsec/audit-check@v2` as a blocking gate (no `continue-on-error`) and fails CI if any unignored vulnerability is found in the dependency tree. Both the `check` and `test` CI jobs are gated on `cargo-audit` via `needs: [cargo-deny, cargo-audit, layer-isolation]`. | Proven | `cargo-audit` job (`.github/workflows/ci.yml`), `audit.toml` |
| CLAIM-2.4  | `cargo geiger --workspace --output-format Json` runs on every CI push/PR and produces a JSON artifact. `scripts/check-geiger.sh` compares the used-unsafe block count against the `geiger-baseline` artifact from the previous successful run and fails CI with old vs. new counts if the count has increased. The baseline artifact is updated on every passing run (90-day retention). The first run (no baseline artifact) passes gracefully and saves the initial count. Both `check` and `test` CI jobs are gated on `cargo-geiger` via `needs`. | Proven | `cargo-geiger` job (`.github/workflows/ci.yml`), `scripts/check-geiger.sh` |
| CLAIM-2.6  | `cargo-public-api` (v0.52.0) runs on every CI push/PR for all library crates (`tirbase-types`, `tirbase-core`, `tirbase-guard`, `tirbase-drivers`, `tirbase-sim`, `tirbase-demo`). `scripts/check-public-api.sh` compares the generated public API against the committed `public-api.txt` manifest in each crate directory; any new `pub` item not in the manifest causes CI failure with the offending item listed. Binary-only crates (`tirbase-admin`, `tirbase-gateway`) are excluded — `cargo-public-api` requires a lib target. Both `check` and `test` CI jobs are gated on `public-api` via `needs`. To approve an intentional API addition, run `cargo +nightly public-api -p <crate> > <crate>/public-api.txt` and commit the updated manifest. | Proven | `public-api` job (`.github/workflows/ci.yml`), `scripts/check-public-api.sh` |
| CLAIM-G1.4 | Revocation delta applied on a mesh node causes subsequent deltas from the revoked DID to be rejected at `apply_incoming_delta` | Proven | `revoked_author_mesh_delta_rejected_at_apply_incoming_delta` |
| CLAIM-G1.5 | `core_activate_saturate_mode` has a real production caller path wired through the init-time `SaturateModeStateMachine` configuration in `CoreHandle::init`; two real `CoreHandle` instances verify the full activation path; removing the root CA key wiring from `CoreHandle::init` causes the test to fail | Proven | `saturate_mode_wiring_two_core_handle_instances_activate_via_production_caller` |
| CLAIM-G1.6 | Cloud-sync send path (`CoreHandle::init` → `spawn_cloud_sync_loop` → `run_cloud_sync_cycle` → `cloud_sync_loop` → `CloudConnection::send_delta`) and receive path (`CloudLedger::receive_delta` via `CloudLedgerConnection::send_delta`) are wired as production callers; a mock cloud endpoint integration test verifies both paths; removing either caller causes the test to fail | Proven | `cloud_sync_send_and_receive_paths_are_wired_to_mock_endpoint` |
| CLAIM-G1.9 | A revocation delta arriving while a migration is executing causes `finish_migration` at `migration/mod.rs:400` (CLAIM-G1.9 block) to discard the transform result before the schema hash advances; the check is verified by a two-`CoreHandle` integration test; removing the `is_revoked` re-check inside `finish_migration` causes `migration_mid_flight_revocation_two_core_handle_instances` to fail (schema advances to `v2` instead of remaining at `v1`) | Proven | `migration_mid_flight_revocation_two_core_handle_instances` |
