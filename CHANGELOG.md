### Added
- **DATEV / Xero / QuickBooks closed accounting connectors (POS-17, proprietary):** a separate sold product staged only in the git-ignored `closed/pos-accounting/` tree, linking nothing from the AGPL runtime and depending only on the Apache-2.0 `tirbase-integrations` POS contract. `accounting-datev`, `accounting-xero` and `accounting-quickbooks` each implement the open `PosConnector` Accounting and E-invoicing families and export journals, invoices, payments, refunds and payouts to the package's documented HTTP surface (DATEV bookings/invoices/credit-notes via a configured gateway with optional Berater/Mandant headers, Xero manual journals/invoices/credit notes, QuickBooks company-scoped journal entries/invoices/credit memos). `acct-sdk` supplies an explicit `ChartOfAccounts` and tax-code mapping (no fallback, no guessed default): resolving an unmapped account or tax key is a permanent refusal naming the key, the tenant and the remedy, queued for operator attention, so an export never guesses a ledger account. Stable external ids (`TB-JRN/INV/PAY/RFD/POT-*`) and derived idempotency keys are deterministic functions of connector, tenant, kind and business reference; `AccountingState` returns the original settled result marked `Replayed` (same remote reference and amount) with no second HTTP call, which is the POS-17 "re-export does not duplicate journals" condition. The export book and error queue record every attempt, surface a reconciliation report (accepted/replayed/retryable/permanent, exported totals, outstanding records) and queue permanent or exhausted-retry failures with their remedy until a corrected re-export of the same reference succeeds. Amounts stay integer minor units formatted as exact two-decimal strings for an allowlisted currency set. Each connector passes the open `certify_pos` conformance suite over real loopback HTTP plus a mock contract suite asserting the documented request shapes, idempotent re-export, unmapped-account refusal with a clear error, payment/refund/payout export and reconciliation; sandbox suites are `#[ignore]` and need operator credentials from the environment. `closed/pos-accounting/docs/` carries setup and per-connector guides, credentials, failure recovery and a support runbook; `scripts/check-pos-accounting.py --test` fails on tracked files, a vendor SDK, a credential shape, a Luhn-valid card-number-shaped run or a missing document, then runs the closed suites.
- **Stripe Terminal / Adyen / SumUp closed connectors (POS-16, proprietary):** a separate sold product staged only in the git-ignored `closed/pos-terminals/` tree, linking nothing from the AGPL runtime. `terminal-stripe` registers a reader (`POST /v1/terminal/readers`) and mints a Terminal connection token, creates a PaymentIntent with `capture_method=automatic` for a sale or `manual` for auth-then-capture, captures (`/capture`), voids (`/cancel`) and refunds (`POST /v1/refunds`), verifies `Stripe-Signature: t=…,v1=…` as HMAC-SHA256 over `"{t}.{raw_body}"` accepting any `v1` entry during rotation with a 300 s signed-timestamp window, and reduces a payout plus balance transactions to a settlement batch where each line's `net` must equal `amount - fee` and the payout must equal the sum of the nets. `terminal-adyen` reassigns a terminal through Management API `POST /v3/terminals/{terminalId}/reassign`, pays (`/v1/payments`, `captureDelayHours: 0` for a sale), captures, cancels and refunds through `/v1/payments/{paymentPspReference}/*` (the pspReference, not the intent id), verifies Adyen's eight-field colon-joined HMAC with the **hex-decoded** Customer Area key and base64 encoding, de-duplicates on `pspReference:eventCode` because standard notifications carry no signed timestamp, and keeps commission, markup, scheme fees and interchange as separate fee kinds in settlement details rows. `terminal-sumup` pairs a reader with its 8–9 character code, starts a reader checkout, refunds through `/v1.0/merchants/{merchant_code}/payments/{transaction_id}/refunds` with an exact major-unit body, and — because SumUp checkout webhooks are **not signed** — refuses to invent a signature: `verify_sumup_signature` always returns `Unsigned` and `confirm_notification` re-reads the transaction from `/v2.1` and requires the status, amount and currency to match before accepting the event id. Capture and void on SumUp are explicit permanent refusals naming the processor reason (a reader checkout captures at the reader; there is no void). `pos-sdk` supplies the transport seam, `ResultLedger` (a replay returns the original reference, amount and detail marked `Replayed`, with no second HTTP call, which is the POS-16 replay acceptance condition), `PaymentBook` (over-capture, over-refund and void-after-capture are refused before the processor sees them, and a retryable failure does not consume the local amount), `WebhookGuard`, exact integer settlement arithmetic that refuses an over-precise or self-disagreeing report, redacted request logging and a loopback processor for the contract tests. Each connector passes the open `certify_pos` conformance suite over real loopback HTTP plus a contract suite asserting the documented request shapes, the replay rule, the webhook checks and the settlement arithmetic; sandbox suites are `#[ignore]` and need operator credentials from the environment. `closed/pos-terminals/docs/` carries setup, credentials, failure recovery, a support runbook, `pci-scope.md` (card-data boundary, controls, residual risks, no compliance claim) and `pci-review-record.md` (internal engineering review: twelve checks, five accepted findings, four open items, and an explicit statement that no QSA assessment was performed); `scripts/check-pos-terminals.py --test` fails on tracked files, a processor SDK, a credential shape, a Luhn-valid card-number-shaped run or a missing document, then runs the closed suites.
- **EN 16931 e-invoicing adapter (POS-15, Apache-2.0):** new `tirbase-en16931` crate maps a POS register invoice onto the EN 16931 semantic model and writes UBL 2.1 Invoice/CreditNote or UN/CEFACT CII D16B, with no dependency on the AGPL runtime (only `serde`, `serde_json`, `sha2` and `hex`; the XML writer and reader are in-crate). `model::Invoice` keeps money in minor units, quantities in thousandths and rates in basis points, so every derived figure — line gross and net, VAT per category and rate, all totals — is integer arithmetic through one half-up rounding step, and `Date::from_unix_seconds` derives a date with the civil-from-days algorithm so nothing reads a clock, the environment or a locale. `pos::PosInvoice` is the register shape (tenant, number, issue/due instants, parties, lines with VAT category and rate, line and document discounts, prepayment, rounding, payment means, refund reference); `to_invoice` apportions a document discount over the VAT groups it applies to with largest-remainder rounding so the breakdown still adds to BT-109, maps a refund to a type-381 credit note naming the invoice it corrects, and reports every input problem at once instead of the first. `ubl` and `cii` serialize deterministically — fixed declaration, two-space indentation, schema element order, two-decimal amounts, `unitCode` quantities, `format="102"` dates — and `xml` is the writer plus a strict reader. `validate` parses the document back and checks well-formedness, requirement, element order, namespaces, datatypes, code lists and every figure against the model that produced it (rule ids follow EN 16931 where the rule is the same, `XML-*`/`MODEL-*` otherwise); the official XSDs are not vendored, so schema validation with an XSD processor remains a deployment step and is documented as such. `profiles::CountryProfile` is the only country extension point: a closed module supplies BT-24/BT-23, content for the standard UBL `ext:UBLExtensions` container, national rules and a final `wrap`, and the crate ships only `en16931-core`, making no national fiscal claim (a test scans every source module for national regimes and asserts the documents carry no URL, platform identifier or profile element). `batch::export` writes `<number>.<syntax>.xml` plus a `manifest.json` with each file's SHA-256 and size, writes no timestamp, sorts every collection, and refuses to write a document that did not validate. The `en16931` binary offers `export`, `validate` (a whole batch, or one exported file against its invoice) and `version`. Golden invoices for tax, discount, refund and rounding are committed with their exact expected UBL and CII bytes and re-validated by `tests/golden.rs`, which also proves byte-identical determinism and a closed-profile extension. `docs/compliance/pos-15-en16931-adapter.md` is the implementation record and `docs/connectors/en16931-export-guide.md` the usage guide.
- **Generic POS integration framework (POS-14, Apache-2.0):** `tirbase_integrations::pos` gives a closed POS connector a surface with no AGPL edge. `PosConnector` groups the five families — `authorize`/`capture`/`void`/`refund`, `post_entry`, `issue_invoice`/`credit_note`, `create_delivery`/`cancel_delivery`/`delivery_status`, `quote_tax`/`verify_tax` — behind twelve typed requests and one `OperationResult` (`Accepted`/`Replayed`/`Retryable`/`Permanent`, with the vendor reference, recorded amount, `Retry-After` and a secret-free detail); unsupported families default to `Permanent`, and `execute(PosOperation)` dispatches for the runtime and the suite. `PosOperation::validate` is the single invariant gate (positive integer minor-unit amounts in one currency, refund reason, balanced double-entry journal, whole-quantity invoice lines, derived idempotency key) and is re-checked by the runtime before every attempt. `ConnectorConfig::from_toml` validates the schema version, connector name, unique non-empty family list, an `https` endpoint (loopback HTTP only with explicit `allow_insecure_loopback`), the timeout range, the retry and reconciliation sections, `env:`/`file:` secret *references* (never values, and a card-named secret is refused) and the embedded CC-20 mapping document, which also shapes vendor payloads via `apply_mapping`. `pos_idempotency_key(connector, kind, reference)` hashes a domain separator into `pos-` plus 32 hex so a retry, restart or replay presents the same key. `PosRuntime` owns the pending and dead-letter queues: `submit` deduplicates (`AlreadyQueued`/`AlreadySettled`), `flush` retries with bounded exponential backoff (honouring a longer `Retry-After`) and dead-letters a permanent failure or an exhausted budget while keeping the payload, attempts and key, `replay` re-enqueues with the same key and refuses a letter whose operation has since settled, and every attempt emits one redacted `LogRecord` plus counters. `pos::pci` makes card data unrepresentable in the model: `PaymentMethodToken` refuses PAN-shaped values and prints `***`, `PosError`'s `Display` scrubs card-shaped runs, and `scrub_card_data`/`contains_card_data` back both the error path and the checks. Reconciliation hooks (`ReconciliationSource`) compare the register's netted settlements with the vendor report and name `missing_remote`, `missing_local`, `duplicate_remote`, `amount_mismatch` (tolerance and currency aware) and `unsettled` references. Mocks enforce the real rules: `MockPaymentTerminal` (dedupe, over-capture/over-refund refusal, settlement netting, injected failures, optional wrong-amount report), `MockAccountingApi` (balance, duplicate reference, replay), `MockDeliveryPlatform` (book/cancel/status, replay) and `MockTaxAuthority` (half-up 21%/10%/0% quotes and verified totals), with `MockPosVendor` composing all five for the suite. `certify_pos` runs the conformance suite — identity, families, capabilities, health, `authorize`, `amount-echo`, `replay`, `amount-mismatch-capture`, `amount-mismatch-refund`, `void-after-capture-refused`, `journal-balance`, `credit-cap`, delivery lifecycle, tax quote/verify and a `no-card-data` scan — and certifies only a connector that reports duplicates and amounts honestly. Apache `tests/pos14.rs` (21 tests) proves certification of the reference vendor, rejection of a connector that ignores replay and of one that accepts an over-capture, the runtime's retry/dead-letter/replay and wrong-amount handling, reconciliation both ways, the mocks, and a Luhn scan that fails the build if a card-number-shaped fixture appears in `src/pos`, the fixtures or the POS-14 documents. `docs/connectors/pos-connector-guide.md` is the build guide and `docs/compliance/pos-14-generic-pos-integration-framework.md` the implementation record. `tirbase-integrations` is now a workspace member, so the crate (and its AGPL-free dependency proof) actually builds.
- **Notifier conformance suite (CC-25, Apache-2.0):** `tirbase_notify::conformance` adds the certification suite every closed alert connector runs against a provider sandbox or mock. `certify(transport, target, tenant, checked_est)` returns a `NotifierReport` with four checks: **identity** (bounded, whitespace-free channel name), **delivery** (the provider accepts a critical alert), **replay** (the same alert is accepted as the same page with the same provider id, never a second page) and **fresh** (a different alert produces a different provider id). It deliberately grades neither wording nor escalation policy, which remain per-connector configuration documented and tested by the product suites; the tenant parameter exists because tenant-bound connectors must refuse sample alerts from another tenant. Unit tests cover a transport that deduplicates correctly and one that pages twice.

- **Sensor/controller HIL validation campaign (CC-22):** AGPL `tirbase_sim::hil` is the software bench half of the HIL programme (F-13). `run_campaign(seed)` drives the production paths for all six CC-22 transports — DS18B20 through `Ds18b20Sensor` on the simulated 1-Wire bus, 4–20 mA through `CurrentLoopCalibration`/`FaultDetector`, BLE GATT through the central boundary and climate decoder, BACnet/IP through `GuardBacnetReader` against the loopback device server, Modbus RTU through the framing codec, and Modbus TCP through `ModbusTcpClient` against the register server — and returns a seeded `CampaignReport` sealed with a SHA-256 digest over its canonical case list. Cases cover the bench matrix (acquire, decode, conversion timing, and refusal of bad CRC, short reads, absent probes, malformed characteristics, truncated or corrupted RTU frames), accuracy against reference values with per-transport tolerances (DS18B20 ±0.5 °C, 4–20 mA ±16 µA, BLE ±0.2 °C/±0.5 %RH, BACnet 10⁻¹ °C, Modbus at register resolution), the documented environmental envelope (datasheet temperature range, 60 °C/85 %RH offset, 2 g vibration pick-up, brownout below the 3.6 mA threshold and brownout-corrupted serial frames), network-loss recovery at acquire time for every transport (loss classified, fresh read after recovery, never a cached value), and a seeded 1,000-cycle stability run that injects a fault every 97th cycle and requires every fault to be classified and every clean cycle to be in tolerance. `verify_recovery` reopens a gateway database and reports `PRAGMA integrity_check`, calibration count, ledger entries and the recomputed chain; `tirbase-sim/tests/hil_campaign.rs` uses it after killing a real child process inside an open `BEGIN IMMEDIATE` write, proving a power cut during a calibration or ledger write rolls back atomically (or keeps a committed record complete) with integrity and the hash chain intact. The evidence pack `docs/evidence/hil/cc22-sensor-controller-validation/` holds the procedure, the reference `campaign.json` (43 cases, seed 22, digest `013e920e…`) and `power-cut.json` for all four durability boundaries, and its committed digest is rechecked against a fresh run so results stay reproducible from the documented command. Lab execution against physical instruments, climate chamber, vibration table and smart PDU remains commercial/operator responsibility per `docs/hil-lab-checklist.md`.
- **Reports, audit UI, data integrity and e-signatures (CC-21):** AGPL `tirbase_gateway::reporting` adds six reports — `excursion_history`, `quarantine_aging` (age buckets new/aging/critical), `disposition`, `calibration_due` (current/due_soon/overdue from the latest calibration per asset), `lot_traceability` (lots, edges, operations, dispositions) and `export_verification` (re-derived verdicts) — generated read-only from the tables the excursion, lot, asset-registry and lineage-ledger modules own. Every row carries the `SourceRef`s it was read from (record, transition event, lot row/edge/operation/disposition, calibration, asset version, and ledger entries whose digest is the ledger's own `entry_hash`), the report holds the deduplicated union, and the content digest (`TirBase/v1/ReportContent`) mints a deterministic `rpt-<hex>` id so regenerating identical content is idempotent. Each generation stores nine ALCOA+ checks with evidence: attributable (generator plus per-row sources), legible, contemporaneous (no source post-dates the generation), original (digest recomputes), accurate (source digests well-formed), complete, consistent (unique keys), enduring (stored and audited) and available. The e-signature ceremony re-verifies identity before signing: signers enroll a credential SHA-256, `open_ceremony` requires a re-authentication inside a 900 s window and an 8–512 character reason, wrong or stale proofs are refused (`ReauthFailed`/`ReauthNotFresh`) and audited, and `sign_ceremony` signs a canonical payload binding report id, content digest, signer, ceremony nonce, reason and instant with Ed25519 exactly once — a second signature returns `CeremonyAlreadyUsed`, a changed report returns `RecordChanged`, and `verify_signature` recomputes the digest from the stored rows so tampering or replaying the signature onto another report fails. Exports render deterministic CSV, JSON and dependency-free paginated PDF, and sign a manifest carrying the report and body digests, row count, exporter and public key (`TirBase/v1/ReportManifest` / `TirBase/v1/ReportBody`); `verify_export` recomputes both and re-verifies the signature, and the verification report re-derives every verdict. `report_audit` is an append-only hash chain (`TirBase/v1/ReportAudit`) over every generation, export, signature, refused re-authentication and retention action; `verify_audit_chain` recomputes every link and names sequence, previous-hash and entry-hash breakage. `prune_export_bodies` drops only export bodies older than a cut-off (keeping digests, manifests, signatures and the chain) and records what it pruned, while `snapshot_to` takes a consistent `VACUUM INTO` copy from which the audit chain, generations, signatures and pruned bodies restore. Apache-2.0 `console/src/screens/AuditScreen.tsx` (via `console/src/audit.ts`) adds the audit UI: report list with ALCOA+ and kind filters, report detail with signatures and chain-of-custody source count, the audit trail, and a verify-chain action, localized in English and Spanish. AGPL `tests/reports.rs` proves the three acceptance conditions — a report traces to its source excursion events and ledger `entry_hash`es, an e-signature cannot be reused for another record (single-use ceremony, digest-bound payload, tamper-detecting verification), and audit records survive retention (body pruning leaves generations, signatures and a valid chain) and restore from a snapshot — plus idempotent regeneration, tenant isolation and the CSV/JSON/PDF exports. The `/admin/reporting/*` surface the audit screen calls is mounted in the shared admin dispatcher, so the local socket and the mTLS listener use the same credential model: an unverifiable remote credential is `401 ADMIN_CREDENTIAL_REQUIRED`, a verified role other than Auditor/PolicyAuthority is `403 ADMIN_CREDENTIAL_INSUFFICIENT`, and writes are `405`. `tenant` is required (`400` when absent) and is never inferred from a result set: listings are filtered by it, and a report detail or signature list for another tenant answers `404` exactly like an unknown id; tenant audit views resolve the tenant's report, export, signature and ceremony subjects, leaving gateway-level enrollment, pruning and verification rows out. The binary mounts the service when `report_signing_seed_path` holds a 64-hex Ed25519 seed and answers `503` otherwise, and `tests/reporting_http.rs` drives all five endpoints through a loopback HTTP listener into the real dispatcher for two tenants. See `docs/reporting.md`.
- **Generic integration framework (CC-20):** new Apache-2.0 `tirbase-integrations` gives closed vendor connectors a surface with no AGPL edge: `Connector` (`name`, `kind`, `capabilities`, `deliver`, `health`) returns one `DeliveryResult` per attempt classified `Delivered`/`Duplicate`/`Retryable`/`Permanent`, and `tests/agpl_free.rs` walks `Cargo.lock` from the crate, refuses any `tirbase-*` direct dependency, and cross-checks its denylist against `LICENSING.md`. The mapping DSL is versioned TOML (`schema_version = 1`, `[[field]]` target/source/required/default/transform) resolved against `{event, payload}` with dot paths and array indexes, producing nested JSON for every transport; validation rejects unsupported versions, duplicate or malformed targets, sources outside `event`/`payload`, and a required field with a default. Generic connectors are `HttpConnector` (POST/PUT/PATCH, `Idempotency-Key`, mapping or raw body), `WebhookConnector` (HMAC-SHA256 over `"<timestamp>.<body>"`), `MqttConnector` (injected `MqttTransport`, in-crate MQTT 3.1.1 PUBLISH encoding with varint remaining length and packet ids), `CsvConnector` (one RFC 4180 row file per idempotency key, atomic temp+rename) and `SftpConnector` (injected `SftpSession`, put-if-absent `<dir>/<key>.json`, `..`-free remote paths); HTTP status classification treats 2xx/409 as accepted or duplicate, 408/425/429/5xx as retryable (honouring `Retry-After`) and 400/401/403/404/410/413/415/422 as permanent. `DeliveryEngine` owns `Outbox` + `RetryPolicy` + `Metrics` + logs: submission deduplicates on event id (`AlreadyDelivered`/`AlreadyQueued`), retries use bounded exponential backoff from the number of failed attempts, a permanent failure or an exhausted budget moves the record to the `DeadLetter` queue with its payload, attempts and idempotency key, and `replay`/`replay_all` re-enqueue with the *same* key while refusing a dead letter whose event has since been delivered, so a replay is a downstream duplicate rather than a second record. Auth is OAuth2 client credentials (cached until `expires_in - 30s`, form-encoded, no clock reads), mutual TLS (`MutualTls::client_builder` adds the CA and identity PEM and fails closed on missing or malformed material), API keys and HMAC webhooks with a constant-time compare and a bounded timestamp skew; `SecretString`, `ApiKey` and `MutualTls` print `***` and zeroize. Observability: one redacted `LogRecord` per attempt (payload never logged, `Bearer`/`key=value` secrets masked, detail truncated), `MetricsSnapshot` counters (attempts, delivered, duplicates, retries, dead letters, replays), and a `HealthSnapshot`/`HealthResponse` document returning 200 for `ok`/`degraded` and 503 for `unhealthy`. `MockVendorServer` is a real loopback HTTP/1.1 fixture that enforces API key, bearer, HMAC or OAuth2 client auth, records every request, deduplicates on `Idempotency-Key` (409 on the second) and injects failures; `conformance::certify` runs the standard contract suite (identity, capabilities, payload ceiling, health, deliver, duplicate, fresh event, oversized payload) and certifies only a connector that reports duplicates honestly. Apache `tests/integration_framework.rs` proves delivery and mapping through the mock, backoff-then-deliver with a driver-visible attempt count, dead-letter → replay → one downstream record and a refused second replay, HMAC acceptance and forged-signature rejection, OAuth2 token caching with a fail-closed wrong secret, API-key and mTLS refusal, CSV/MQTT/SFTP idempotency, certification of the real HTTP connector and rejection of a connector that claims success for everything, and redacted logs with health tracking pending work and dead letters.
- **Multi-site fleet and tenant isolation (CC-19):** AGPL `tirbase_gateway::fleet` adds a tenant-scoped fleet of sites, rooms, containers and gateways in `primary.db`, keyed by an F-03 `TenantPath` and authorized by a `CapabilityScope`. Every read is authorized *and* filtered to the caller's tenant subtree (`tenant_fact = ? OR substr(tenant_fact, 1, length(?) + 1) = ? || '/'`), so isolation does not depend on the caller; a direct read of another tenant's node, key, config, rollout or export fails with `CrossTenantDenied` rather than returning an empty result, expired capabilities fail with `CapabilityExpired`, and writes need `write` inside the scope. Isolation covers **data** (`list_nodes`, `fleet_view`, `get_node`, paginated by node id with a clamped page size and total count), **keys** (`TenantKeyRef` holds only a SHA-256 fingerprint and purpose — never key material — and `tenant_keys` is subtree-scoped), **configs** (`TenantConfig`, `config_drift`) and **exports** (`export_tenant` produces a deterministic `exp-<digest prefix>` record with a domain-separated digest; `list_exports`/`read_export` require `audit_read` and deny other tenants). `fleet_view` and `site_status` roll nodes up per site: worst health and compliance, per-health counts and non-compliant counts, plus fleet totals. ### Fixed
- **Demo-pack launcher checks timed out on build-lock contention:** each pack's `run.sh` spawned a nested `cargo test`, which competes with the running `cargo test` for the build directory and pushed the launchers past their 120 s budget (129 s+ even on an idle tree). Launchers now run a prebuilt test binary when the caller provides one (`TIRBASE_DEMO_TEST_BIN`, set by the pack tests to their own executable) and fall back to cargo for standalone use, the pack tests run their launchers one at a time instead of six in parallel, and they assert that the checks really executed (`test result: ok`, never `0 passed`) so the faster path cannot pass by skipping work.
- **Cumulative drift window double-counted one segment:** Stage 13 summed the window from the newest sample instead of the oldest, adding a phantom `|oldest - newest|` term that rejected legal step sequences early. The window now sums consecutive deltas only, so a slow ramp is rejected exactly when it crosses the profile's budget. Covered by the cold-room `S2_slow_ramp` scenario.
- **Stage 16 dwell/min-off summary read the post-write state:** `SqliteStage16Store` upserted `target_state` before reading the previous value, so `value_changed` and `is_bool_deactivation` were always false and the `drift_rate_summary` timing columns never advanced. The previous value is now read before the write, restoring dwell and min-off interlocks (cold-room `S2_door_abuse`, `S2_compressor_short_cycling`, `S1_defrost_manipulation`).
- **CRDT array/list convergence:** `CrdtEngine` now stores JSON arrays as real Automerge lists (RGA-capable) and projects list values as JSON arrays on read/merge/projection, fixing a defect exposed by real-mesh concurrent list insertion proof.
